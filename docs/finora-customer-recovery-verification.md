# FINORA — استرجاع طلبات حفظ العملاء بعد إعادة التشغيل

تاريخ التنفيذ: 2026-10-11. تطوير محلي في FINORA Desktop؛ لا نشر للخادم أو تحديث مثبّت الإنتاج، ولا اعتماد لاكتمال ERP.

## السلوك

يحفظ Electron الطلب الأصلي على القرص قبل إرسال أوامر واجهة العملاء عبر `/api/v1/desktop/customers/...`. تشمل الحماية إضافة وتعديل الملف، تسجيل الدين الافتتاحي، إنشاء جدول فاتورة، تقسيم أقساط خطة موجودة، وتعديل مواعيدها وقيمها. مفتاح UUID والمرجع والمبلغ والسبب وإصدار المصدر والجدول تبقى كما أرسلت؛ لا يصنع الاسترجاع طلباً بمفتاح جديد.

إذا انقطع الرد أو أُغلق البرنامج قبل استلامه والتحقق منه، تظهر «طلبات الحفظ المحفوظة» في صفحة العملاء. تعرض سبب العملية والمرجع والمبلغ وعدد الأقساط أو جدول المواعيد، وبيانات الملف عند تعديل العميل. يراجع المستخدم البيانات ثم يضغط «تأكيد نفس الطلب». يعاد الطلب الأصلي ويعيد الخادم نتيجته المحفوظة أو ينفذه ضمن المعاملة الأصلية. بعد التحقق الكامل من مخطط الرد، يغلق العميل الطلب المحلي ويحدث البيانات من الخادم. لا يكتب الرد التاريخي فوق جدول أحدث أثناء الاسترجاع من القائمة.

تأكيد الخادم والتأكيد المحلي خطوتان منفصلتان: نجاح الخادم وحده لا يحذف الطلب. رد غير مكتمل أو فشل تأكيد التخزين أو إغلاق renderer يبقيه للمراجعة. فشل حفظ نقطة الاسترجاع يمنع الإرسال، ولا يستخدم النقل الشبكي طريقاً بديلاً يتجاوز التشفير.

زر التأكيد ثابت بأسفل النافذة، وتظل مراجعة البيانات قابلة للتمرير. عند وجود عدة طلبات يختار المستخدم الطلب المطلوب وتعرض منطقة التأكيد اسمه. نافذة الاسترجاع تعلو ملف العميل المفتوح، وفتحها من فوق نموذج إضافة أو تعديل مقفل حتى يغلق المستخدم النموذج، دون إلغاء بياناته تلقائياً. يحافظ التصميم على SidePanel ودرجات FINORA والحركة الحالية ودعم تقليل الحركة وشرح `?`.

## العزل والحماية

- قاعدة Offline الموجودة مشفرة بـAES-256-GCM، ومفتاحها محفوظ عبر حماية Windows في `safeStorage`. إعادة استخدام القاعدة والمفتاح لا تنشئ مخزناً نصياً جديداً للطلبات. فشل فتح المفتاح أو القرص لا يحذف القاعدة ولا يسمح بإرسال طلب عميل غير محفوظ.
- هوية المخزن تشمل الخادم والشركة ومعرفها والموظف والفرع ونطاق الفروع. الانتقال لشركة/فرع آخر أو تسجيل الخروج يخفي الطلبات ويحفظها لهويتها الأصلية. رد قديم يحمل هوية تأكيد محلية ولا يستطيع إغلاق طلب بنفس UUID في شركة أخرى.
- كل إرسال واسترجاع يحتاج تحقق جلسة حي من الخادم والصلاحيات الحالية. جلسة Offline المخزنة لا تفوض كتابة مالية. إضافة الدين تتطلب صلاحيات إدارة العملاء وعرض وإعداد الحسابات؛ بقية الأوامر تتطلب إدارة العملاء، ويعيد الخادم التحقق من المصدر والفرع والإصدار والفترة المحاسبية.
- الطلب بنفس UUID وبيانات مختلفة مرفوض. طلب جديد لنفس المصدر غير المؤكد مرفوض محلياً؛ تعديل وتقسيم نفس الخطة يشتركان بالحماية. إضافة عميل غير مؤكدة تمنع إضافة ثانية حتى تأكيد الأولى؛ تعديل ملفات مختلفة يظل مستقلاً.
- يرفض النقل مسارات العميل غير المعروفة أو المشفرة في URL قبل إرسالها. قنوات الاسترجاع تقبل UUID ومدخل تأكيد مضبوطاً فقط، وتستخدم فحص renderer الموثوق الموجود.
- يرفض renderer المحدث إرسال أمر العميل إذا كان main/preload القديم لا يوفر جسر الاسترجاع، مع طلب إعادة تشغيل النسخة المحدثة. لا يعلن الحماية ثم يرسل من نسخة لا تدعمها.
- رفض أعمال صريح لأول محاولة فقط يمكنه إزالة الطلب المحلي؛ الرفض عند إعادة طلب غير مؤكد يبقيه. لا توجد خاصية حذف طلب غير مؤكد أو مزامنة تلقائية له. الحد 100 طلب لكل هوية؛ يجب مراجعتها قبل إضافة المزيد، والقائمة لا تخفي بعضها خلف حد قراءة أصغر.

اختبارات المخزن تفحص فتح القاعدة من جديد، عدم وجود المرجع/UUID بالنص على القرص، فشل نقطة الحفظ قبل الإرسال وبعد التزام الخادم، تعديل البيانات والتكرار والتزامن، العزل وتغير الصلاحيات، الرد المشوه، هوية التأكيد القديمة، وموانع المسارات غير المسموحة. اختبارات الواجهة تفحص مراجعة الطلب وشرح `?` ومنع الاسترجاع Offline وعدم تأكيد رد مشوه أو فاقد لهوية التأكيد.

اختبار Electron يستخدم ملف مستخدم مؤقتاً مستقلاً وخادماً تجريبياً: يطبق الخادم الطلب ويحجب رد التأكيد حتى تنتهي مهلة العميل وينقطع الاتصال، يغلق Electron ويعيد تشغيله بنفس الملف، ثم يسترجع نفس البيانات وUUID ويتحقق من اختفاء الطلب بعد التأكيد وبقائه غير مرسل بعد إعادة تحميل الواجهة. يفتح ملف العميل قبل الاسترجاع للتحقق من ترتيب النوافذ، ويتحقق من ظهور المبلغ أو التاريخ الأصلي وزر التأكيد بالكامل في المقاسات الثلاثة. المصدر المالي الحقيقي يتحقق باختبارات Python في قواعد شركات معزولة؛ fixture واجهة Electron ليس دليلاً محاسبياً مستقلاً.

## الحدود والمتبقي

هذا تعافٍ للطلبات التي بدأ إرسالها أثناء الاتصال، وليس إنشاء ديون أو خطط أو ملفات عملاء Offline. لا تسترجع طلبات أجهزة أخرى، ولا طلباً فُقد ملفه المحلي ومفتاحه معاً. عند فقدان الصلاحية أو تعارض مستمر يبقى الطلب للمراجعة؛ يرجع المستخدم إلى الشركة والفرع الأصليين وبصلاحية صالحة. لا توجد تسوية إدارية تلقائية أو حذف لطلب لا تعرف نتيجته.

تحصيل العميل عبر سند الحسابات يستخدم المسار المالي القائم؛ هذه الدفعة لا تعلن اكتمال التعافي لجميع أوامر الحسابات. تبقى مصادر الدين الجديدة غير الافتتاحية، والكشف التاريخي الكامل لأصل الدين والتعديل والمرتجعات والرصيد المتسلسل، والعملاء Offline، وبقية مراحل ERP. فحص Python العام السابق (2114 ناجحاً، 59 إخفاقاً، 10 متجاوزة) لا يغلق بهذه البوابة المحددة؛ لا يصنّف كل إخفاقاته قديمة أو محلولة.
