# جدولة المتبقي من فاتورة ذات تحصيل مباشر سابق — 2026-10-11

هذا تقرير الدفعة السابقة وحدودها حين اختبرت. أضيف بعده دعم سندات الحسابات السابقة والمعكوسة مع ربط مستقل وحفظ عكس الأصل؛ التقرير الحالي في `finora-customer-voucher-history-verification.md`.

من ملف العميل يمكن إنشاء جدول لفاتورة مسددة جزئياً بتحصيل مباشر سابق أو رصيد قديم غير مفصل. تعرض المعاينة أصل الفاتورة والمدفوع المحفوظ والمتبقي، وصفاً واضحاً للتحصيل السابق، ثم الأقساط الجديدة فقط. التصميم ونافذة الجدولة والشرح `?` والحركات تستعمل مكونات FINORA القائمة.

## أثر العملية

- الفاتورة تبقى مصدر أصل الدين. لا يتغير أصلها أو مدفوعها، ولا يضاف قبض أو سند أو حركة مخزون أو قيد أو تخصيص مالي عند إنشاء الجدول.
- يضاف صف أقساط ملخص بقيمة المدفوع السابق ومدفوع مماثل؛ تاريخ هذا الصف هو تاريخ الفاتورة للتوثيق، وليس استحقاقاً جديداً أو ادعاءً بتاريخ دفع جميع المبالغ. مجموع الصفوف يساوي أصل الفاتورة، ومجموع المدفوع يساوي مدفوعها.
- إذا وجد سجل تحصيل مباشر مطابق، تُنسخ حصصه الموجبة والسالبة إلى سجل دفعات الأقساط مع التاريخ الأصلي ومرجع `[IP:invoice]` ورقم سجل المصدر. سجلات الفاتورة الأصلية وحساباتها ووسائلها تبقى كما هي. لا تنسخ ملاحظات خارجية إلى علامات تخصيص سندات الحسابات.
- إذا لا يوجد سجل تفصيلي، يوثق رصيد قديم غير مفصل بتاريخ الفاتورة دون اختراع وسيلة دفع أو حساب أو موظف أصلي. لا يكتب سجل تحصيل جديد؛ مسارات التحصيل التالية تستعمل أساس الرصيد القديم القائم.
- العدد يخص الأقساط الجديدة فقط؛ صف التحصيل المحفوظ يدخل ضمن سقف 240 صفاً، ولذلك حد العدد الجديد لهذه الفاتورة 239. الفرق العددي يذهب إلى القسط الأخير، والتكرار الشهري يحافظ على يوم الاستحقاق مع آخر يوم بالشهر الأقصر.
- بعد الإنشاء تعمل مسارات تعديل تحصيل الفاتورة وسند التحصيل الجديد وعكسه مع الجدول ذاته. إعادة تقسيم المستقبل لا تحذف هوية صف مرتبط بتحصيل، حتى بعد عكس الدفعة.

## الحماية والحدود

- يلزم مستخدم نشط وشركة الجلسة وصلاحية إدارة العملاء وفرع فاتورة مسموح. لا قراءة أو جدولة لفاتورة عميل آخر أو فرع خارج النطاق.
- تمنع الفواتير الملغاة والمرتجعة والمقفلة للمخزون وذات جهة تحصيل شحن أو جدول قائم. المسددة بالكامل لا يوجد لها متبقٍ لهذه العملية.
- مجموع سجل التحصيل يجب أن يطابق مدفوع الفاتورة. أثر غير صفري بصافي صفر، أو أعمدة/تواريخ ناقصة تمنع إثبات المصدر، أو علامة صفر لا تفسر مدفوعاً موجباً، يحتاج مراجعة ولا يحول إلى قبض مفترض. المعاينة تتعامل مع الأعمدة الموجودة فعلياً دون ترقية قاعدة قديمة عند GET.
- **السندات المالية السابقة غير مدعومة بعد**: أي تخصيص `invoice` من الحسابات أو سجل `finance:<voucher>` يبقي الإنشاء محظوراً بسبب واضح. لم تُعدل تخصيصات سند مرحّل ولم تُضف حصصاً بأثر رجعي إلى سند قديم؛ يلزم مسار مستقل يضمن عكس الأصل قبل فتح هذه الحالات.
- بصمة المصدر تشمل رصيد وحالة وفرع الفاتورة وتاريخها وسجلات التحصيل بمبالغها وتواريخها ووسائلها وحساباتها وعلامة المصدر، وتخصيصات الحسابات. تغيير البيانات بعد المعاينة يعطي تعارضاً.
- قيد مصدر الفاتورة ومعرّف الطلب ونسخ الدفعات وصفوف الأقساط والتاريخ قبل/بعد تحفظ في معاملة واحدة. فشل سجل النشاط يتراجع عن النسخ كلها؛ إعادة نفس الطلب تعيد نفس النتيجة ولا تعيد قبضاً أو تنشئ خطة ثانية.
- التعافي من رد غير معروف ما زال محصوراً بنافذة النموذج ومفتاحها في الذاكرة؛ التخزين المشفر والاسترجاع بعد إعادة تشغيل التطبيق وOffline للعملاء لم يكتمل.
