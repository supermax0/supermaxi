# FINORA Desktop — نظام إدارة الفروع المتقدم (المواصفة المحفوظة)

الحالة: **قيد التنفيذ** — بدأ بتاريخ 2026-10-15. التقرير والتقدم: `docs/finora-multi-branch-phase0-report.md`.

## ملاحظات أولية قبل البدء (من العمل السابق على المشروع — تُراجع في المرحلة 0)

FINORA يحتوي مسبقاً على أساس للفروع، فالمطلوب **توسيعه لا إنشاؤه من الصفر**:

- نموذج `Branch` و`BranchStock` و`StockTransfer` في `models/branch.py`.
- `branch_id` موجود على جداول كثيرة (الفواتير، المصاريف، الصناديق `treasury_account`، الشحن، المندوبين، الموظفين…).
- مفتاح الوضع `independent_branches_enabled()` في `utils/branch_mode.py` + نطاق ORM تلقائي حسب الفرع (`g.branch`, `skip_branch_scope`, `utils/branch_scope.py: resolve_write_branch_id`, `utils/branch_context.init_branch_context`).
- ترحيل الفروع v2 (`utils/branch_migration.py`، `get_default_branch`) — **تنبيه:** نسخة `tenants/super_production_pull.db` فيها ترحيل v2 معطوب (KeyError في `_localize_suppliers`)؛ يجب الاختبار دائماً على **نسخة**.
- تحويلات المخزون بين الفروع موجودة في `modules/stock_operations` (مسودة/إرسال/استلام، طبقات FIFO، سجل تدقيق، سندات تلف).
- تطبيق سطح المكتب: `desktop/finora_management` (Electron + React + TS + TanStack Query)، الـ API الخاص به في `modules/desktop_api` و`/api/v1/desktop/…`.
- التقارير v2 تدعم فلتر فرع عبر ضبط `g.branch` مؤقتاً (`services/reports_service.py`).
- الأقفال المالية: `utils/financial_period_guard.py`، دفتر موحد `modules/finance` (قيود، سندات، `FinanceMapping`).

## المواصفة الكاملة كما كتبها المستخدم

FINORA Desktop — نظام إدارة الفروع المتقدم
Full Multi-Branch Management System — Production Implementation

### الدور المطلوب
أنت مهندس برمجيات أول، ومهندس أنظمة محاسبية، ومهندس قواعد بيانات، ومتخصص بتطوير الأنظمة متعددة الشركات والفروع (Multi-Tenant / Multi-Branch ERP).
مهمتك تطوير نظام فروع متكامل داخل تطبيق FINORA Desktop الحالي، مع المحافظة التامة على الوظائف والبيانات والسلوك المحاسبي الموجود.
هذا مشروع قائم يعمل بالفعل، وليس مشروعاً جديداً. ممنوع إعادة بناء النظام من الصفر أو استبدال بنيته الحالية دون ضرورة مثبتة.
نفّذ الميزة كامتداد احترافي للنظام الحالي، مع دعم التوسع إلى عدد كبير من الفروع والمخازن والمستخدمين.

### المرحلة 0: تحليل المشروع قبل أي تعديل
1. افحص هيكل المشروع بالكامل.
2. حدد تقنية الواجهة والخادم وقاعدة البيانات ونظام المزامنة.
3. افحص طريقة تعريف الشركة والمستأجر (Tenant).
4. حلل بنية الحسابات والقيود ودفتر الأستاذ.
5. افحص جدول الفواتير وتفاصيلها والمدفوعات والمرتجعات.
6. افحص المخزون والمنتجات والمخازن والمشتريات.
7. افحص الموظفين والصلاحيات.
8. افحص الصناديق وسندات القبض والصرف والتحويل.
9. افحص الطلبات والشحن والمندوبين.
10. افحص طريقة العمل Offline/Online إن كانت موجودة.
11. حدد الخدمات المشتركة التي تعتمد عليها العمليات المالية والمخزنية.
12. حدد جميع العلاقات بين الجداول والخدمات وواجهات API قبل تعديلها.

أنشئ تقريراً داخلياً يحتوي على: خريطة المعمارية الحالية، جداول قاعدة البيانات المرتبطة، مسارات تنفيذ العمليات المحاسبية، نقاط إضافة معرف الفرع، مخاطر التوافق مع البيانات القديمة، خطة ترحيل آمنة، الاختبارات المطلوبة قبل وبعد التطوير.
استخدم التقنية والمكتبات الموجودة بالمشروع، ولا تضف إطار عمل جديداً إلا بوجود حاجة فعلية. لا تنفذ تغييرات تدميرية، ولا تستخدم أوامر حذف البيانات أو إعادة تهيئة قواعد البيانات.

### المرحلة 1: فلسفة نظام الفروع
نظام الفروع داخل FINORA يجب أن يكون اختيارياً بالكامل. ثلاثة سيناريوهات:

**السيناريو A: شركة قديمة** (فواتير، منتجات ومخزون، أرصدة صناديق، حسابات عملاء وموردين، موظفين، مشتريات ومبيعات، مصاريف، مرتجعات، مستندات، طلبات قيد التنفيذ):
اعتبار الشركة فرعاً أساسياً واحداً افتراضياً دون تغيير بياناتها المالية. تستمر جميع العمليات والتقارير بنفس الطريقة. لا يظهر محدد الفرع إذا كانت الميزة غير مفعّلة. لا تجبر الشركة على إنشاء فروع. عند التفعيل وإنشاء فرع جديد يمكن استخدام معالج خاص (اختياري) لتوزيع جزء من البيانات الحالية.

**السيناريو B: شركة جديدة**: إنشاء فرع أساسي تلقائياً؛ ربط جميع العمليات الجديدة به داخلياً؛ إبقاء تعدد الفروع غير مفعّل افتراضياً؛ عند التفعيل السماح بإنشاء فروع مباشرة؛ عدم إظهار معالج نقل البيانات التاريخية أو إعدادات الترحيل نهائياً؛ الفرع الجديد بدون حركات أو أرصدة افتراضياً؛ استخدام التحويلات الرسمية لنقل بضاعة أو أموال. لا تعرض رسالة ترحيل أثناء إنشاء شركة جديدة.

**السيناريو C: شركة قديمة تفعل الفروع بدون نقل بيانات**: احتفظ بجميع البيانات القديمة داخل الفرع الأساسي؛ أنشئ الفرع الثاني فارغاً؛ ابدأ العمليات الجديدة على الفرع المطلوب؛ لا تعدّل الأرباح أو الأرصدة القديمة؛ لا تجبر على معالج التوزيع.

**قاعدة أساسية:** لا يجوز أن يؤدي تفعيل الفروع وحده إلى إنشاء أرباح أو مصاريف أو إيرادات أو التزامات جديدة.

### المرحلة 2: التوافق الخلفي (إلزامية)
يجب أن تبقى الشركات الموجودة تعمل بنفس طريقتها:
1. لا تغيّر طريقة حساب أرباح الشركة. 2. لا تغيّر أرقام الفواتير التاريخية. 3. لا تعِد إنشاء القيود القديمة. 4. لا تصفّر المخزون أو تعيد تكوينه. 5. لا تغيّر حسابات العملاء والموردين. 6. لا تغيّر صلاحيات الموظفين دون طلب. 7. لا تغيّر أرصدة الصناديق. 8. لا تغيّر طريقة التسديد والقبض. 9. لا تغيّر نتائج التقارير القديمة. 10. لا تظهر إعدادات فروع لمستخدم الفرع الواحد إلا عند الحاجة.

قبل التفعيل وبعده يجب أن يبقى مجموع الأرصدة والموجودات والالتزامات والأرباح مطابقاً تماماً (ما لم توجد معاملات تشغيلية جديدة فعلية). ترحيل تدريجي آمن وقابل لإعادة التنفيذ (Idempotent). أي حقل فرع جديد له سياسة واضحة للسجلات القديمة. ممنوع كسر واجهات API أو الوظائف الحالية.

### المرحلة 3: هيكل الفروع وقاعدة البيانات
التسلسل: Company / Tenant → Branches → Warehouses → Cash Registers → Employees and Operations. كل فرع يتبع لشركة واحدة؛ للشركة فروع كثيرة؛ كل فرع عدة مخازن وصناديق.

**بيانات الفرع:** المعرف، معرف الشركة، كود فريد داخل الشركة، الاسم، الاسم المختصر، النوع، الحالة، أساسي أم لا، المحافظة، المدينة، العنوان، الإحداثيات (اختيارية)، الهاتف، البريد، اسم المدير، العملة الافتراضية، المستودع الافتراضي، الصندوق الافتراضي، المنطقة الزمنية، إعدادات الطباعة، ترقيم الفواتير، تاريخ بدء التشغيل، الإنشاء والتعديل، المنشئ، بيانات الأرشفة.
**الأنواع:** فرع مبيعات، معرض، مركز توزيع، مستودع، مركز خدمة، مقر إدارة. (نوع الفرع لا يعني أن كل مستودع فرع — الفصل بين الكيان التشغيلي والموقع التخزيني.)

**الجداول المقترحة (حسب المعمارية):** branches، branch_settings، branch_user_assignments، branch_permissions، branch_transfer_requests، branch_transfer_items، branch_transfer_events، branch_cash_transfers، branch_initial_distribution_sessions، branch_initial_distribution_items، branch_initial_distribution_audits، branch_daily_closings.
استفد من الجداول المحاسبية والمخزنية الموجودة؛ وسّع الـ Stock Ledger / General Ledger / Cash Transactions لدعم الفروع. **دفتر أستاذ موحد** يصدر تقارير حسب الفرع ومركز التكلفة (لا دفتر منفصل لكل فرع).

**العلاقات:** أضف معرف الفرع للسجلات ذات النطاق التشغيلي الحقيقي: الفواتير، الطلبات، المشتريات، المصاريف، حركات المخزون، سندات القبض والصرف، العمليات النقدية، التسويات، الجرد، الشحن، القيود أو تفاصيلها. لا تضف branch_id عشوائياً. المنتج مشترك على مستوى الشركة والكمية على مستوى المخزن/الفرع. العميل والمورد موحدان على مستوى الشركة مع مسؤولية المتابعة حسب الفرع. فهارس مركبة (tenant_id, branch_id, التواريخ) مع عزل بيانات الشركات.

### المرحلة 4: إعدادات تفعيل الفروع
المسار: الإعدادات ← إعدادات الشركة ← إدارة الفروع ← الإعدادات المتقدمة. مفتاح «تفعيل تعدد الفروع» (افتراضياً غير مفعّل).
- **غير مفعّل:** وضع الفرع الواحد؛ لا محدد فرع في POS؛ لا أعمدة فروع غير ضرورية؛ لا صفحات تحويل؛ كل العمليات على الفرع الأساسي؛ واجهات مطابقة للسلوك الحالي.
- **مفعّل:** إدارة الفروع؛ إضافة فروع؛ مخازن وصناديق لكل فرع؛ صلاحيات الفروع؛ تقارير لكل فرع؛ التحويلات؛ محدد نطاق العمل في الشريط العلوي.
لا يُسمح بإيقاف الميزة بطريقة تمسح الارتباطات بعد وجود معاملات متعددة الفروع (بديل: وضع عرض مبسط أو معالج دمج رسمي).

**خيارات متقدمة:**
- عامة: تفعيل الفروع، الفرع الأساسي، أكواد الفروع، تعدد مخازن الفرع، الفرع الافتراضي للمستخدم، الفرع على الفواتير المطبوعة، الفرع في التقارير، تفعيل/تعطيل الفروع غير النشطة، ترقيم المستندات لكل فرع.
- المخزون: السماح بالتحويل، موافقة مدير المصدر، موافقة المستلم، البضاعة بالطريق، التحويل الجزئي، فروقات الاستلام، منع المخزون السالب، المخزن الافتراضي، الحجز والمتاح، صلاحية إلغاء التحويل.
- المحاسبة: تقارير لكل فرع، تقارير موحدة، صناديق مستقلة، مشاركة الحسابات البنكية المركزية، تحويل الأرصدة النقدية، اعتماد تحويلات النقد، مراكز تكلفة الفروع، توزيع المصاريف المركزية، إقفال يومي لكل صندوق، إقفال مالي حسب الصلاحيات.
- المبيعات والطلبات: الفرع المصدر، فرع تجهيز الطلب، البيع من مخزون فرع آخر، طلبات بين الفروع، سياسة المردودات، صلاحية تعديل فرع الفاتورة، صلاحية عرض فواتير الفروع الأخرى، التحصيل المرتبط بالفرع.
- الموظفون: مدير الفرع، تعيين الموظفين، الموظف متعدد الفروع، الفرع الافتراضي، صلاحية التنقل، صلاحية عرض الأرباح، صلاحية التحويل المالي والمخزني.
كل خيار يُحفظ بأمان في إعدادات الشركة ويُطبّق على **الخادم** وليس الواجهة فقط.

### المرحلة 5: معالج التوزيع الأولي (للشركات القديمة فقط)
لا يظهر للشركات الجديدة. يظهر فقط للشركات القديمة المؤهلة (بيانات تشغيلية قبل دعم الفروع) عند اختيار المدير. الأهلية بحالة محفوظة/إشارة ترحيل موثوقة، لا بتاريخ الإنشاء وحده.
حالات الجلسة: غير مستخدم، مسودة، قيد المراجعة، جاهز للتنفيذ، قيد التنفيذ، مكتمل، فشل يحتاج معالجة، ملغى قبل الاعتماد. لا تنفيذ للجلسة مرتين.

1. **إنشاء الفرع:** الاسم، الكود، النوع، الموقع، المدير، الصندوق الافتراضي، المخزن الافتراضي.
2. **اختيار البيانات (لا شيء مختار افتراضياً):** المخزون، الأموال والصناديق، الموظفون، الفواتير، الطلبات، العملاء والموردون، الحسابات والذمم، المستندات والمرفقات، المصاريف والتصنيفات التاريخية (عند السماح). لكل فئة صفحة تفصيلية.
3. **المخزون:** كود، اسم، المخزن المصدر، المتاح، المحجوز، المطلوب تحويله، كلفة الوحدة وفق سياسة المخزون، القيمة، المخزن المستلم؛ بحث وفلترة وتحديد جماعي؛ لا تكرار للمنتج؛ النقل بحركة مخزون موثقة مع الحفاظ على التقييم والكلفة (مثال: 20 شاشة، نقل 7 ⇒ 13 + 7 = 20).
4. **الأموال:** الصندوق المصدر، المستلم، المبلغ، التاريخ، السبب، الملاحظات، المعتمد. لا تعديل مباشر للرصيد؛ حركة تحويل داخلية ذات طرفين؛ تحقق الرصيد والصلاحيات (20 مليون، نقل 5 ⇒ 15 + 5 = 20). التحويل ليس مصروفاً ولا إيراداً.
5. **الموظفون:** نقل، إضافة الفرع لفروع الموظف، إبقاء، تحديد الافتراضي؛ الحفاظ على الرواتب والسلف والاستقطاعات والدوام والإجازات والصلاحيات والتاريخ الوظيفي مرتبطة بالفترة والفرع الصحيحين.
6. **الفواتير:** فلاتر (التاريخ، العميل، الرقم، الحالة، مسددة/غير مسددة/جزئياً/مرتجعة، مرتبطة بطلب، مرتبطة بشحن). خياران: (أ) **نقل مسؤولية المتابعة** — يبقى أصل الفاتورة وإيرادها وكلفتها كما هو؛ (ب) **إعادة التصنيف التاريخي** — بصلاحية وضوابط، لا بمجرد تحديث branch_id؛ تحليل القيد والتفاصيل والكلفة والمخزون والتحصيلات والتسديد الجزئي والمرتجعات والخصومات والذمم والفترات المغلقة؛ منع ازدواج الإيراد؛ لا تغيير صامت للمستندات المنشورة؛ الفترة المغلقة وفق سياسة الإقفال والتصحيح.
7. **العملاء والموردون:** يبقون على مستوى الشركة؛ تغيير الفرع المسؤول، مسؤول المتابعة، الفرع الافتراضي، صلاحية الاطلاع، توزيع الفواتير والأرصدة المفتوحة عند الحاجة؛ لا تكرار؛ لا نقل للديون بتعديل الرصيد يدوياً.
8. **المستندات:** المرفقات، الطلبات، الملفات الإدارية، المستندات غير المالية، السندات المرتبطة، الوثائق الداعمة؛ دون قطع الارتباط بالفاتورة أو القيد؛ حفظ تاريخ المصدر ومن أعاد الإسناد.
9. **المعاينة:** عدد المنتجات، الكميات، قيمة المخزون، مبالغ الصناديق، عدد الموظفين والفواتير والحسابات، الذمم، المستندات، العلاقات التابعة، التعارضات، غير القابل للنقل، الأرصدة قبل/بعد، الأثر على التقارير. حالة كل عنصر: جاهز / يحتاج مراجعة / غير مسموح. منع التنفيذ مع وجود مخالفات محاسبية.
10. **الاعتماد والتنفيذ:** نسخة استعادة، سجل عملية فريد، تثبيت لقطة الاختيارات، إعادة التحقق من الأرصدة والكميات، معاملات قاعدة بيانات، تنفيذ قابل للاستئناف، منع التكرار، إظهار النجاح فقط بعد الاكتمال والتحقق، تقرير تفصيلي. عند الفشل: تراجع آمن أو حالة استئناف واضحة دون أرصدة مضللة.

### المرحلة 6: صفحة «الفروع والمخازن» (RTL، بهوية FINORA)
- **بطاقات علوية:** الفروع النشطة، مبيعات الشركة، مجمل الربح، صافي الربح (عند اكتمال الحسابات فقط)، قيمة المخزون، إجمالي النقد، قيد التحصيل، التحويلات المعلقة.
- **قائمة الفروع:** الاسم، الكود، الموقع، المدير، الحالة، المبيعات، مجمل الربح، قيمة المخزون، رصيد الصندوق، الطلبات المفتوحة، آخر نشاط.
- **تفاصيل الفرع (تبويبات):** نظرة عامة، المبيعات، المخزون، الصناديق، الموظفون، الطلبات، المصاريف، التحويلات، التقارير، الإعدادات.
- **شريط إجراءات:** تعديل الفرع، عرض المخزون، تحويل بضاعة، تحويل أموال، إضافة موظف، كشف الفرع، طباعة تقرير، إيقاف الفرع.

### المرحلة 7: محدد الفرع العام (الشريط العلوي عند التفعيل)
«جميع الفروع ▼» أو «فرع الكرادة ▼»: بحث سريع، جميع الفروع (للمخولين)، الفروع المسموحة، الافتراضي، الحالة، اختصار تبديل. عند التبديل تتحدث المبيعات والطلبات والمخازن والإحصائيات والتقارير والصناديق حسب الصلاحيات.
**الفصل بين نطاق العرض ونطاق إنشاء العملية:** «جميع الفروع» = عرض مجمع فقط؛ أي عملية جديدة تحتاج فرعاً تشغيلياً واحداً صالحاً ومخزناً وصندوقاً مناسبين. التحقق على الخادم دائماً.

### المرحلة 8: التحويلات المخزنية بين الفروع
البيانات: الرقم، الشركة، الفرع/المخزن المصدر، الفرع/المخزن المستلم، المنتجات، الكميات، الكلفة، السبب، الملاحظات، المستخدم، أوقات الإنشاء والإرسال والاستلام، المرفقات.
الدورة: مسودة → طلب اعتماد → معتمد → قيد التجهيز → تم الإرسال → بالطريق → استلام جزئي/كامل → مكتمل (+ الرفض والإلغاء والفشل).
حالات خاصة: قطعة واحدة، عدة منتجات، كمية جزئية، استلام أقل، تلف أثناء النقل، فقدان قطعة، رفض الاستلام، إرجاع للمصدر، إلغاء قبل الإرسال، معالجة تحويل مُرسل.
التحويل ليس بيعاً ولا يخلق إيراداً أو ربحاً. **البضاعة بالطريق:** بعد الإرسال غير متاحة في المصدر، وقبل الاستلام غير متاحة في الوجهة؛ تبقى ضمن موجودات الشركة. **التزامن:** منع بيع الكمية مرتين بقفل/تحقق على الخادم.

### المرحلة 9: التحويلات المالية بين الفروع
الحقول: الفرع/الصندوق المصدر، الفرع/الصندوق المستلم، المبلغ، العملة، التاريخ، المرجع، السبب، الحالة، الموافق، المستلم، الملاحظات.
الضوابط: عدم تجاوز الرصيد (إلا بسياسة صريحة)، منع التحويل للصندوق نفسه، منع التكرار، عدم اعتماد غير المكتمل، مطابقة المصدر والوجهة، سجل تدقيق، الاستلام الجزئي فقط إن كان صحيحاً محاسبياً.
الأثر: حركة متوازنة؛ ليس مصروفاً ولا مبيعات ولا يدخل الأرباح. الحسابات البنكية المركزية: فصل مالك الحساب عن نطاق الفرع المسؤول؛ لا تكرار للرصيد البنكي في كل فرع.

### المرحلة 10: نقطة البيع POS
فرع تشغيلي محدد عند الفتح. كل بيع يحفظ: الفرع المصدر، المخزن، صندوق التحصيل، الموظف، التفاصيل، الكلفة، حالة الدفع. التحقق من رصيد المخزن المختار لا مجموع الشركة. عند عدم التوفر: عرض التوفر بالفروع الأخرى، طلب تحويل، تجهيز من فرع آخر حسب السياسة، أو طلب يحتاج تجهيزاً. البيع من الكرادة والتجهيز من المنصور: حفظ فرع البيع، فرع التجهيز، المخزن الفعلي، فرع التحصيل، والإسناد المحاسبي للإيراد والكلفة — بسياسة مركزية دون مضاعفة.

### المرحلة 11: الطلبات والشحن والمندوبون
الطلب: فرع الإنشاء، فرع التجهيز، المخزن المصدر، مسؤول البيع، جهة التحصيل، المندوب، شركة النقل.
دعم: تحويل مسؤولية الطلب، تجهيز لفرع آخر، الشحن من مخزن محدد، إرجاع الشحنة للمخزن الصحيح، فرع تحصيل أموال شركة النقل، تسوية كشوف المندوبين وشركات النقل حسب الفرع. عند الرجوع: لا تفترض الرجوع لفرع الفاتورة؛ حدد مخزن الاستلام الفعلي ثم عالج المردود والمخزون والذمة. لا تسديد جديد لمجرد تغيير الفرع المسؤول.

### المرحلة 12: الحسابات العامة والعملاء والموردون
دفتر موحد مع تقارير حسب الفرع. حساب العميل: جميع الفروع أو فرع معين، الفواتير، التسديدات، المردودات، الديون، الفرع المسؤول — دون مضاعفة الرصيد. المورد بنفس المبدأ (فرعان يشتريان من نفس المورد دون تكرار). دعم القيود ذات الفرع/مركز التكلفة. سياسة واضحة للعمليات المشتركة والمصاريف المركزية.

### المرحلة 13: المصاريف والرواتب
ثلاثة أنواع: خاص بفرع، إدارة رئيسية، مشترك. قواعد التوزيع: نسبة ثابتة، نسبة المبيعات، عدد الموظفين، المساحة، يدوي — مع الحفاظ على إجمالي المصروف وعدم تسجيله مرتين.
الرواتب: الموظف لفرع أو عدة فروع؛ سجل انتقالات بتواريخ سريان؛ تحميل الراتب على فرع أو توزيعه؛ لا تغيير صامت لكشوف الرواتب السابقة.

### المرحلة 14: الجرد المتعدد الفروع
جرد فرع، جرد مخزن، جرد كل الفروع، مقارنة الأرصدة، تتبع الفروقات، مراجعة التحويلات بالطريق، اكتشاف منتجات موجودة بفرع آخر، الطلبات المعلقة المؤثرة على المتاح، تقرير الفاقد والزيادة. نقص بفرع وزيادة بآخر: لا تسوية تلقائية؛ اعرض التطابق والمستندات والتحويلات المحتملة؛ تصحيح معتمد عند ثبوت نقل غير مسجل، وإلا وفق سياسة تسويات الجرد.

### المرحلة 15: تقارير الفروع
- مالية: المبيعات، المرتجعات، صافي المبيعات، كلفة البضاعة، مجمل الربح، مصاريف الفرع، صافي نتيجة الفرع، النقد المتاح، الذمم المدينة والدائنة، التحصيلات، المدفوعات، المبالغ بالطريق.
- مخزون: القيمة، المتوفر، الناقص، حركة المنتج، التحويلات، البضاعة بالطريق، الجرد والفروقات.
- أداء: مقارنة الفروع، المبيعات حسب الموظف، متوسط الفاتورة، عدد الطلبات، الملغاة، المرتجعة، سرعة التجهيز، الربحية حسب الفرع.
واجهة مقارنة لفترة وفرعين أو أكثر بجداول ورسوم بسيطة؛ لا جمع مكرر؛ عرض موحد يستبعد الازدواج الداخلي؛ توضيح شمول مصاريف الإدارة المركزية أو عدمه.

### المرحلة 16: الموظفون والصلاحيات (توسيع RBAC الحالي)
صلاحيات: عرض الفروع، إنشاء، تعديل، أرشفة، مشاهدة بيانات فرع، مشاهدة كل الفروع، تبديل الفرع التشغيلي، تحويل مخزون، اعتماده، استلامه، تحويل أموال، اعتماده، مشاهدة الأرباح، مشاهدة الصناديق، إدارة الموظفين، إعدادات الفروع، معالج التوزيع، إعادة تصنيف بيانات تاريخية.
أدوار مقترحة: مدير عام، مدير فرع، محاسب، كاشير، مسؤول مخزن، موظف مبيعات، موظف شحن. كل صلاحية مرتبطة بنطاق (شركة، فروع محددة، فرع، مخزن/صندوق). منع تغيير branch_id يدوياً عبر API؛ كل الاستعلامات مقيدة بالشركة أولاً ثم بنطاق الفرع.

### المرحلة 17: Offline والمزامنة
كل عملية محلية تحمل: الشركة، الفرع، الجهاز، المستخدم، معرف عملية فريد، التوقيت، إصدار المزامنة/حل التعارض.
منع تكرار الفواتير والتسديدات وتحويلات المخزون والسندات بعد إعادة الاتصال؛ معالجة التعارضات؛ استئناف المزامنة. آخر قطعة بيعت من جهازين Offline: سياسة صريحة (حصص مسبقة للأجهزة أو اعتبار إحداهما بانتظار تأكيد التجهيز) دون حذف فاتورة أو قبض بصمت. التحويلات التي تحتاج موافقة واستلاماً لا تكتمل محلياً.

### المرحلة 18: التصميم وتجربة الاستخدام
هوية FINORA Desktop: Light افتراضياً، خلفية بيضاء/رمادية فاتحة، خطوط عربية واضحة، RTL كامل، ألوان الهوية، حدود خفيفة، زوايا مدورة باعتدال، ظلال خفيفة، مسافات متناسقة، عناصر صغيرة بلا ازدحام، حركات قصيرة ناعمة، مكونات التصميم الموجودة، دعم أحجام النوافذ. لا لوحة تحكم منفصلة، ولا تغيير كامل للتنقل.
معالج التوزيع (Stepper): بيانات الفرع → اختيار الفئات → السجلات والكميات → مراجعة العلاقات → معاينة التأثير → التأكيد والتنفيذ → التقرير النهائي؛ الرجوع قبل الاعتماد؛ حفظ مسودة دون حركات؛ جداول ببحث وفلاتر وتحديد متعدد؛ المجاميع دائماً؛ لا اختيار لما لا يملك المستخدم صلاحيته.
الأداء: تحميل عند الحاجة، Pagination/Virtualization، بحث بالخادم، فهارس، تجنب N+1، مجاميع من مصادر مالية موثوقة، حالات تحميل وأخطاء واضحة، تحديث آمن دون إعادة تحميل التطبيق.

### المرحلة 19: حماية البيانات والتدقيق
كل حركة حساسة تحفظ: معرف العملية، الشركة، الفرع المصدر/المستلم، المستخدم، النوع، الوقت، الحالة السابقة والجديدة، السبب، مرجع المستند، النتيجة. لا حذف صامت للحركات المعتمدة (إلغاء أو قيد عكسي). حماية من التنفيذ المكرر. فصل الإنشاء والموافقة والتنفيذ والاستلام والإقفال مع تتبع المنفذ. اختبار عزل الشركات.

### المرحلة 20: اختبارات إلزامية
- A — الشركات القديمة (مبيعات، مشتريات، مخزون، ديون، صندوق، موظفين، مرتجعات، طلبات معلقة): التفعيل لا يغير أي إجمالي مالي.
- B — الشركات الجديدة: فرع أساسي داخلي، لا معالج توزيع، تشغيل بسيط، إنشاء فرع، لا حركات مالية عند إنشاء فرع فارغ.
- C — النقل المختار: منتج واحد، عدة منتجات، مبلغ مالي، موظف، تعيين فاتورة للمتابعة، فئات محددة فقط، إلغاء المعالج، إعادة فتح المسودة، التنفيذ، منع إعادة التنفيذ؛ الفئات غير المختارة لا تتأثر.
- D — سلامة الحسابات: ثبات إجمالي النقد والمخزون والأرباح، لا ازدواج قيود أو ذمم، توازن القيود، صحة تقرير كل فرع والتقرير المجمع.
- E — الفواتير: مسددة، غير مسددة، جزئية، مرتبطة بمردود، بطلب وشحن، ضمن فترة مغلقة؛ نقل المتابعة لا يغير الإيراد أو الربح.
- F — الصلاحيات: مدير عام، مدير فرع، كاشير، مسؤول مخزن، وصول لفرع غير مصرح، وصول لشركة أخرى — رفض من الخادم.
- G — التزامن: انقطاع الشبكة أثناء التنفيذ، إعادة إرسال الطلب، تعارض نقل المخزون، تكرار استلام التحويل، مزامنة فاتورة مرتين، استئناف العمليات المتوقفة.

### المرحلة 21: ترتيب التنفيذ
- Sprint 1 — تحليل وتأسيس: التحليل، توثيق العلاقات، المخاطر، تصميم الجداول، إعدادات الشركة، الفرع الأساسي، التوافق الخلفي.
- Sprint 2 — إدارة الفروع: إنشاء، تعديل، أرشفة، إعدادات، القائمة، التفاصيل، محدد النطاق.
- Sprint 3 — المخزون والتحويلات: ربط المخازن، المخزون حسب الفرع، التحويل، البضاعة بالطريق، الاعتماد والاستلام، الفروقات.
- Sprint 4 — المالية: الصناديق، سندات التحويل، القيود، الحسابات المشتركة، القبض والتسديد، تقارير أرصدة الفروع.
- Sprint 5 — العمليات: POS، الطلبات، المشتريات، المرتجعات، الشحن، الموظفون، المصاريف.
- Sprint 6 — التوزيع الأولي (بعد استقرار الخدمات المالية والمخزنية): الأهلية، الاختيار، العلاقات، المعاينة، التنفيذ، التدقيق، التقرير.
- Sprint 7 — التقارير والحماية: تقارير الفروع، المقارنات، الموحدة، الصلاحيات، سجل التدقيق، الأداء.
- Sprint 8 — الاختبار والإطلاق: شاملة، القديمة، الجديدة، سلامة الأرصدة، الصلاحيات، المزامنة، الأداء، إطلاق تدريجي.
لا يُعتبر أي Sprint مكتملاً قبل نجاح اختباراته أو توثيق أسباب ما لم يُنفذ.

### المرحلة 22: شروط القبول النهائية
الشركات القديمة دون تغيير غير مقصود؛ لا معالج للجديدة؛ فرع أساسي مضمون؛ التفعيل من الإعدادات؛ فروع متعددة؛ تخصيص الموظفين؛ مخزون كل فرع؛ التحويل بين المخازن والفروع؛ تحويل النقد؛ لا تغيّر في الأرباح بسبب التحويل الداخلي؛ اختيار بيانات محددة للتوزيع وبقاء غير المختار؛ معاينة الأثر المالي؛ لا تكرار؛ تقارير موحدة مطابقة؛ تقرير لكل فرع؛ صلاحيات على الخادم؛ عزل الشركات؛ لا مضاعفة بالمزامنة؛ سجلات تدقيق كاملة؛ الواجهات القديمة سليمة؛ الاختبارات الأساسية ناجحة؛ خطة استعادة قبل الإطلاق.

### تعليمات نهائية صارمة
1. افهم النظام أولاً ثم نفّذ. 2. لا تحذف أي وظيفة. 3. لا تُعد كتابة النظام المحاسبي. 4. استخدم المكونات والخدمات الفعلية. 5. لا تستبدل منطق الحسابات دون تحليل أثره. 6. لا بيانات تجريبية ثابتة في الوظائف الإنتاجية. 7. لا نجاح محاسبي قبل تأكيد الحفظ. 8. لا تجاوز للصلاحيات عبر API. 9. لا إعدادات نقل تاريخي للشركات الجديدة. 10. التفعيل غير إجباري. 11. لا أرباح أو مصاريف وهمية عند التحويل. 12. لا تعديل مباشر للأرصدة بدل المعاملات الموثقة. 13. لا دمج لبيانات عدة شركات. 14. لا تكرار للمنتجات بسبب الفروع. 15. بساطة الشركات ذات الفرع الواحد. 16. لا ادعاء لاختبارات لم تُشغّل. 17. قابلية الاختبار والصيانة. 18. ترحيلات تدريجية قابلة للتعافي. 19. إظهار أي خطر بيانات أو محاسبة في تقرير التنفيذ. 20. لا ترحيل إنتاجي تدميري أو غير قابل للرجوع دون حماية واعتماد.

### المطلوب النهائي
نظام فروع متقدم ومتكامل داخل FINORA Desktop يعمل فعلياً مع المحاسبة والمخزون ونقطة البيع والطلبات والموظفين والمشتريات والشحن. الشركات القديمة تحافظ على بياناتها وتستطيع عند الحاجة توزيع أجزاء محددة عبر معالج آمن. الشركات الجديدة تبدأ طبيعياً دون إعدادات ترحيل تاريخي، ويمكنها تفعيل الفروع والتحويل بسندات رسمية. الهدف: الانتقال من شركة بفرع واحد إلى Multi-Branch ERP حقيقي دون التضحية بسلامة البيانات أو سهولة الاستخدام. ابدأ بتحليل المشروع الفعلي، ثم نفّذ مرحلة بمرحلة واختبر كل تكامل، مع تقرير ختامي بالملفات والتعديلات والاختبارات والنتائج والقيود المتبقية.
