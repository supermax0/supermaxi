# Finora Mobile API load evidence — 2026-07-16

This report records measured capacity only. It is not a projection to one
million concurrent users.

## Environment

- Production host: 2 vCPU, 7.8 GiB RAM.
- Gunicorn: `gthread`, 3 workers × 4 threads.
- Nginx TLS proxy with `worker_processes auto`.
- Redis-backed guest discovery cache and shared rate limiter.
- Tenant database: SQLite/WAL for the current validation-stage deployment.
- Probe mix: health, first feed page, first 24 catalog products, categories.

## Results

| Path | Concurrency | Requests | Errors | Throughput | p95 | p99 |
|---|---:|---:|---:|---:|---:|---:|
| Gunicorn localhost | 24 | 240 | 0% | 1,025.92 req/s | 48.61 ms | 55.12 ms |
| Nginx + HTTPS, generator on host | 24 | 240 | 0% | 318.53 req/s | 110.15 ms | 141.99 ms |
| Nginx + HTTPS, generator on host | 100 | 2,000 | 0% | 310.21 req/s | 558.05 ms | 729.08 ms |

The 100-concurrency gate passed the configured requirements of p95 below
1,000 ms and error rate below 1%. Every endpoint is checked independently;
one slow endpoint fails the run even when the aggregate p95 looks acceptable.

A workstation-to-production run showed multi-second tail latency while the
same workload was fast on-host. That result is treated as WAN/load-generator
path evidence, not application processing latency.

## Proven boundary

The current host is verified only through the 100-concurrency public read
stage above. Authenticated writes, comments, checkout and AI require separate
datasets and workload profiles before their own capacity can be claimed.

The next stages must run in an isolated environment with distributed load
generators, PostgreSQL/PgBouncer, object storage/CDN and multiple API nodes.
The single-host SQLite deployment must not be described as million-user ready.
